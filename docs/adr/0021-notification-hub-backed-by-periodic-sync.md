# Notification hub backed by reconnect-first sync fallback

SSHWarden will use the Bitwarden-compatible notification hub as the near-real-time path for vault changes and should not poll aggressively while the WebSocket is healthy. Notification health means the WebSocket upgrade succeeds, the SignalR initial message is accepted, the initial response is received as either text or binary `{}\x1e`, and the connection continues to receive messages or respond to keepalive checks. Because the self-hosted `warden-worker` notification Durable Object does not proactively emit heartbeat messages, SSHWarden sends a SignalR MessagePack ping every 30 seconds and treats the connection as stale if no message, echo, ping, or pong is observed for 90 seconds. When the notification connection is lost, initialization fails, keepalive fails, or the idle timeout is exceeded, SSHWarden first attempts reconnect with exponential backoff; only after repeated reconnect failures or a configured elapsed threshold does it perform a fallback sync when unlocked, or record a pending sync while locked. By default, fallback sync begins after 3 failed reconnect attempts and then runs at the configured degraded cadence (`sync_interval`, default 300 seconds) while notifications remain unavailable. `sync_interval` is therefore a reliability fallback cadence for degraded notification state, not a blind polling loop during healthy WebSocket operation; setting it to zero may disable fallback sync for users who want notification-only operation.
