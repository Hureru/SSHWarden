## Must fix

### 2. After a restart the vault is never synced again — Tested

- **Where:** `src/unlock.rs:231-312`; `crates/sshwarden-api/src/client.rs:332`
  (`set_user_key` has no caller); the failure is at `src/sync.rs:100`. Native
  unlock builds no session at all: `src/daemon.rs:473-477`.
- **Problem:** The session restored after PIN unlock has an access token but not
  the user key (the key that opens vault items). Only a master-password login
  sets it. After restart + PIN unlock, `sync` and every automatic sync fail with
  "Bitwarden session cannot decrypt vault data", a key deleted on the server
  still signs, and `status` says "Bitwarden: logged in". After keyring unlock:
  `authenticated=false`, sync says "Not authenticated".
- **Fix:** at login, store the user key and the refresh token in the session
  file, encrypted with the Local Cache Key. On every unlock, load both and call
  `set_user_key`. This gives native unlock a session too and removes the PIN
  from the session file (item 10). Callers of `save_device_session`:
  `src/daemon.rs:319,562`, `src/unlock.rs:300`, `src/control.rs:958,1195`,
  `src/ui.rs:558`. Do item 19 first.
- **Test to add:** login → stop → start → PIN unlock → change the vault on the
  fake server → `sync` succeeds and the key list changes. Same with keyring
  unlock.

### 3. `login` on a remembered device does not update the saved keys — Tested

- **Where:** `src/sync.rs:55-76`.
- **Problem:** The cache rewrite is skipped silently when the Local Cache Key is
  not in memory, which is the case after restart + `login` (what the error of
  item 2 tells the user to do). The agent gets the new keys, the file keeps the
  old ones, `stale_cache` stays false, and after the next restart a deleted key
  signs again.
- **Fix:** when a cache exists but its key is not loaded, call
  `mark_cache_stale(...)` and say so in the login reply. With item 2 fixed,
  nobody needs `login` after a restart.
- **Test to add:** restart → `login` (no unlock) with a changed vault → the
  reply warns and `status` shows a stale cache.

### 7. While a sync waits on a silent server, the daemon answers nothing — Tested (rest of item 7)

- **Where:** main loop `src/daemon.rs`: the sync on a notification, the
  fallback sync, the token refresh and every control command are awaited
  inline, and the loop reads no signing request meanwhile.
- **Done already:** every HTTP request now ends after 30 s (10 s to connect),
  and `keys ui` runs in its own task. The freeze is bounded and `stop` works.
- **Problem left:** the fake server accepted a sync and never replied. `sync`
  failed after 30.0 s, and a `status` sent 2 s into it waited 28.0 s. Signing
  waits the same way, once per sync attempt.
- **Fix:** after item 19's `DaemonState`, run each sync in its own task (one
  at a time), so the loop keeps serving. Check the lock flag again before the
  synced keys are loaded.
- **Test to add:** a server that accepts and never answers → `status` and a
  signature are answered within a second while `sync` is waiting.

### 23. The session file is deleted on any refresh failure — Tested

- **Where:** `src/unlock.rs:304-310`.
- **Problem:** `session-*.enc` is deleted whenever `refresh_access_token`
  fails, for any reason. With HTTP 503, and with a dropped connection during
  PIN unlock, the file was gone. Later, with the server healthy:
  `authenticated=false` and `sync` → "Not authenticated. Run 'sshwarden login'."
- **Fix:** delete only when the server rejects the token (HTTP 400/401 with
  `invalid_grant`). Keep the file on network errors and 5xx.
- **Test to add:** refresh returns 503 → file still there; returns 400
  `invalid_grant` → file removed.

## Should fix

### 10. The PIN protects less than the code says — Tested (timing), Read (rest)

- **Where:** fixed legacy salt for the session file: `src/unlock.rs:333-334`,
  `crates/sshwarden-api/src/crypto.rs:359-366`. Minimum length 4:
  `src/commands/login.rs:14,186`, `src/control.rs:1161`, `src/ui.rs:528`.
- **Problem:** The session file still uses the fixed public salt that SEC-04
  removed from the cache, so one precomputed table fits every user. One guess
  costs about 100 ms (Argon2id, 64 MiB, 3 passes; measured), so all 4-digit
  PINs take about 17 minutes for anyone holding the files. In multi-device mode
  the files sit in a cloud folder.
- **Fix:** item 2 removes the PIN from the session file. Raise the minimum to 6
  in one shared constant; ask for more when `multi_device = true`.

### 11. Several requests while locked open several PIN windows — Read

- **Where:** `src/ui.rs:118-335`.
- **Problem:** Each sign request that arrives while locked runs the unlock
  alone. Three connections at once (git with submodules, ansible, an IDE) mean
  three PIN windows; after the first unlocks, cancelling the others denies
  their requests.
- **Fix:** one `tokio::sync::Mutex` around the unlock block, then check
  `vault_locked` again, as the key picker does with `picker_lock`.
- **Test to add:** two sign requests while locked → one `UIRequest::PinDialog`.

### 13. Each `login` looks like a new device; 2FA accounts cannot log in — Tested (device id), Read (2FA)

- **Where:** `create_client` in `src/commands/login.rs:50-68`;
  `crates/sshwarden-api/src/client.rs:134-157`.
- **Problem:** Two logins sent two different device ids although the session
  file stores one. The login cannot send a 2FA code or the e-mailed code
  bitwarden.com asks of unknown devices. `[auth] method = "api_key"` in the
  example config is read by nothing.
- **Fix:** reuse the saved `device_id` in `create_client` (3 lines). Then see
  [Decisions](#decisions-needed-first).

### 14. HTTPS calls and the notification socket trust different certificates — Tested

- **Where:** `crates/sshwarden-api/Cargo.toml:17-19`; root `Cargo.toml:42`;
  the manual provider choice at `src/main.rs:52`.
- **Problem:** `reqwest` uses OpenSSL with the system trust store;
  `tokio-tungstenite` uses rustls with built-in public roots. With a server
  certificate signed by a private CA (trusted through `SSL_CERT_FILE`): login
  and sync worked, the notification hub stayed `state=failed`, and the server
  logged 5 handshakes failing with `TLSV1_ALERT_UNKNOWN_CA`.
- **Fix:** one stack. `reqwest` with `default-features = false` and
  `rustls-tls-native-roots`; `tokio-tungstenite` with
  `rustls-tls-native-roots`; `rustls` with `default-features = false` plus
  `ring` (today the default features also pull in `aws_lc_rs`).
- **Gain:** up to 15 packages go away: `native-tls`, `openssl`, `openssl-sys`,
  `openssl-macros`, `openssl-probe`, `foreign-types`, `foreign-types-shared`,
  `hyper-tls`, `tokio-native-tls`, `aws-lc-rs`, `aws-lc-sys`, `cmake`, `dunce`,
  `fs_extra`, `webpki-roots`. Check with `cargo tree` after the change.

### 15. All SSHWarden copies of one user share one keyring entry — Tested

- **Where:** `crates/sshwarden-ui/src/unlock/native.rs:8-10,55-125`. The
  attributes are fixed (`application=sshwarden kind=local-cache-key`) and the
  `slot` argument is ignored.
- **Problem (on a private D-Bus with gnome-keyring 51.1):** instance B
  `set-pin` → instance A `unlock-native` fails with "Failed to decrypt local
  key cache payload". B `forget` → A fails with "Failed to unlock Local Cache
  Key with native unlock". A's PIN still works. So a dev build, a portable copy
  or a second `SSHWARDEN_HOME` breaks the real agent's keyring unlock.
- **Fix:** add a random id when storing, keep it in the slot text that is
  already saved, and use it for lookup and delete.
- **Open:** right after B's `forget`, `stop` returned an empty reply once. Not
  investigated.

### 16. The managed snippet is written next to the program — Tested

- **Where:** `crates/sshwarden-config/src/lib.rs:728-739`; documented at
  `docs/host-bindings.md:11,80`.
- **Problem:** The default is `<program folder>/sshwarden_config`. From a
  read-only folder (like `/usr/local/bin`), `keys bind` fails with "Permission
  denied" after `bindings.json` was already changed.
- **Fix:** default to the data folder for everyone, as multi-device mode does.
  The marked Include line is rewritten to the new path on the next write.
  Update the two doc lines.

### 17. `run --background` stays in the foreground on Linux and macOS — Tested

- **Where:** `src/main.rs:152-157`, `src/process.rs:36-51`.
- **Problem:** Only Windows detaches; elsewhere the flag only sends logs to a
  file. The README's first step looks like a hang. Also: the child that
  `sshwarden restart` starts inherits the caller's stdout and stderr and stays
  in the caller's session (same sid, no `setsid`).
- **Fix:** when stdin is a terminal, start the child with the existing
  `spawn_background_agent` and exit. In that function, give the child null
  stdio and its own session (`setsid`).

### 18. The release job mislabels the Mac build and publishes too early — Read

- **Where:** `.github/workflows/release.yml:33-41,74,98,141,172-173`;
  `GITHUB_ACTIONS.md:23,45` repeat the x64 claim.
- **Problem:** `macos-latest` is an Apple-silicon runner and no `--target` is
  given, so the asset named `macos-x64` is an arm64 program. The public release
  is created before any build runs. No tests run.
- **Fix:** name it `macos-arm64` (or build with `--target x86_64-apple-darwin`),
  create the release as a draft and publish after the uploads, run
  `cargo test --workspace` first.

### 19. The PIN unlock logic exists three times and the copies differ — Read

- **Where:** `src/control.rs:555-662`, `782-887`; `src/ui.rs:226-330`.
  `handle_control_command` is at `src/control.rs:409`, `handle_ui_request` at
  `src/ui.rs:99`.
- **Problem:** Only the first copy upgrades an old cache to the random salt
  (SEC-04); the second never enrolls the keyring slot. The copies exist because
  state is passed as 11 to 19 separate arguments: `resolve_pending_sync(...)`
  is written out at 10 call sites, 14 lines each, and 7 functions carry
  `#[allow(clippy::too_many_arguments)]`.
- **Fix:** one `DaemonState` struct holding those `Arc`s and one
  `unlock_with_pin(&state, pin)` used by all three. About 400 lines less, no
  new layer. Do this before items 2, 3, 11 and 23.

### 25. The Bitwarden user key stays in memory after lock — Tested (rest of item 25)

- **Where:** `api_client` is not touched by `lock_vault` (`src/control.rs`).
- **Problem:** After `lock`, the daemon's memory still holds both halves of
  the user key. (The master password half of this item is fixed: the control
  line and the password/PIN payloads are wiped.)
- **Fix:** in `lock_vault`, drop the user key from the client. This needs
  item 2, so that unlock can load it again; do it in the same commit.

### 26. With the keyring enrolled, `lock` is not a boundary on Linux — Tested (decision needed)

- **Where:** `src/ui.rs:125-173`; ADR 0014 against ADR 0009.
- **Problem:** After `lock`, the next sign request unlocks through the keyring
  with no prompt. With `prompt_behavior = "never"` it signed at once and
  `status` showed `locked=false`. While locked, any process of the same user
  can run `secret-tool lookup application sshwarden kind local-cache-key` and,
  with the cache file, recover every private key without the agent.
- **Note:** the second half is how a login keyring works and cannot be fixed in
  this code. The first half (lock that undoes itself silently) can.
- **Fix:** see [Decisions](#decisions-needed-first). At the least, say it in
  the README and in `sshwarden lock`'s output.

### 27. SIGTERM kills the daemon without clean-up — Tested

- **Where:** only `ctrl_c` is handled: `src/daemon.rs:607`.
- **Problem:** `kill <pid>`, `systemctl stop` and logout leave `sshwarden.pid`,
  `agent.sock` and `control.sock` behind.
- **Fix:** add a `tokio::signal::unix::signal(SignalKind::terminate())` arm
  next to `ctrl_c` (Unix only) that breaks the same loop.

## How to reproduce

The scripts used for the audit lived in `/tmp` and are gone. This is the recipe.

**Never test against a real daemon.** Run the binary with a clean environment:

```sh
env -i PATH=/usr/bin:/bin \
  HOME=$T/home SSHWARDEN_HOME=$T/data SSHWARDEN_LOCAL_HOME=$T/local \
  SSHWARDEN_RUNTIME_DIR=$T/run \
  DBUS_SESSION_BUS_ADDRESS=unix:path=$T/no-bus \
  target/release/sshwarden run
```

- The dead D-Bus address matters: the keyring entry is one fixed slot per user
  (item 15), so a sandbox `set-pin` or `forget` would hit the real one.
- In the sandbox `config.toml`, set `[ssh_config] managed_path` (item 16) and
  `[agent] prompt_behavior = "never"`, so that signing needs no dialog.
- `run` works without a display. Start it as a child process (item 17).
- **Control channel:** write one JSON line `{"cmd":"…"}` to
  `$T/run/control.sock`, shut down the write side, read one JSON line.
  Commands used: `unlock-password:<pw>`, `set-pin:<pin>`, `unlock-pin:<pin>`,
  `unlock-native`, `lock`, `sync`, `status-json`, `forget`, `stop`.
- **Fake Bitwarden server** (about 60 lines of Python `http.server`):
  - `POST /identity/accounts/prelogin` → `{"kdf":0,"kdfIterations":N}`
  - `POST /identity/connect/token` → access and refresh token, plus `Key` for
    the password grant
  - `GET /api/sync` → `profile{id,email,key}` and type-5 ciphers with
    `sshKey{privateKey,publicKey,keyFingerprint}`
  - 404 for the rest (the hub stays "retrying"; a fallback sync fires every
    `[agent] sync_interval`)
  - EncString = `2.b64(iv)|b64(ct)|b64(hmac_sha256(mac, iv+ct))`, AES-256-CBC.
    Master key = PBKDF2-SHA256(password, email); stretch with HKDF-expand
    (info `enc` / `mac`); the 64-byte user key is encrypted with the stretched
    key, vault fields with the two halves of the user key.
- **Signing:** `SSH_AUTH_SOCK=$T/run/agent.sock ssh-keygen -Y sign -f key.pub -n ns file`.
  Keep only `.pub` files in that folder: `ssh-keygen` silently signs with a
  private key file lying next to the `.pub`.
- **Memory scan (items 8, 24, 25):** search `/proc/<pid>/mem` for the secret.
  The reader must be the daemon's parent (`ptrace_scope=1`).
- **Keyring (items 15, 26):** a private bus and keyring:
  `env -i … XDG_RUNTIME_DIR=$T/xdg dbus-run-session -- bash -c 'printf pw | gnome-keyring-daemon --unlock --components=secrets; …'`
- **Hung server (item 7):** accept the connection, read the request, never answer.
- **Private CA (item 14):** serve HTTPS with a certificate from your own CA and
  set `SSL_CERT_FILE` for the daemon.

State at the time of the audit: 114 tests pass;
`cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --check`
are clean.
